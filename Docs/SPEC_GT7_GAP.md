# GT7 との機能差分 — 何が無いか、何を入れるか、何を入れないか

調査日: **2026-09-02**
対象: `grantucorsa`（トヨタ86 ZN6 デジタルツイン / UE5 + 自前物理モデル）
比較対象: **Gran Turismo 7**（Polyphony Digital / Sony Interactive Entertainment）

> **この文書について**
> `Docs/HANDOFF_NEXT_SESSION.md` §2.2 F の作業。
> **GT7 に追いつくための計画書ではない。** GT7 は「見た目と遊びの完成度」を
> 目的にした製品で、このプロジェクトは**物理的整合性**を目的にしている
> （`CLAUDE.md` 冒頭）。目的が違う以上、差分の全てが埋めるべき穴ではない。
>
> だから**「入れない」と決めたものを理由つきで並べる**ことを、この文書の
> 本体とする。書き方は `Physics/setup.py` の `UNSUPPORTED` に揃えた。
> 項目を黙って落とすと、「このプロジェクトにこの機能が無い」のか
> 「実装が抜けている」のかが区別できなくなる。

---

## 0. 先に読む — 出典の扱いと、この調査の限界

### 0.1 出典が取れた範囲（憲法ルール2）

GT7 の仕様は**公式サイト（gran-turismo.com）のみ**を出典とした。
攻略 wiki・動画・掲示板は使っていない。「よく知られている」は出典ではない。

**ただし重大な制約がある。** `gran-turismo.com` のオンラインマニュアルは
JavaScript で本文を描画しており、**HTTP 取得ではタイトルしか返らない。**
実際に取得を試み、失敗している。

したがって出典は2種類に分かれる。§7 の表で**どちらかを必ず明記した。**

| 記号 | 意味 |
|---|---|
| **[本文]** | ページ本文を取得して読んだ。引用の根拠として使える |
| **[索引]** | URL の存在は確認したが、**本文は検索インデックス経由の要約でしか読んでいない。**一次確認に達していない |

**[索引] の項目を「確認済み」と扱わないこと。** 実装に入る前に、
その画面を実機で確認するか、本文を読める手段で読み直すこと。

### 0.2 「GT7 に無い / 確認できなかった」ものは、そう書く

推測で埋めていない。確認できなかったものは §8 に列挙した。

### 0.3 判定に使った基準

各機能を、この3つのどれかに分類した。

| 区分 | 意味 | 根拠 |
|---|---|---|
| **入れる** | このプロジェクトの目的（物理的整合性の検証と提示）に寄与する | — |
| **条件つき** | 入れてよいが、**演出であることを明示し、検証には使わない** | 憲法ルール18（仕様と演出の分離） |
| **入れない** | 入れると捏造・ライセンス違反・目的からの逸脱になる | 憲法ルール1・2・4、`PHASE15_DATA_LICENCE.md` |

**「あると楽しいから入れる」は判定理由にならない。**
このプロジェクトで最も高くつく失敗は、出典の無い数値が実測値の顔をして
入り込むことである（`Docs/AGENT_TOPOLOGY.md` §3・§4）。

## 2. 機能差分 — 走行支援・アシスト

### 2.1 ABS / TCS / ASM / カウンターステアアシスト

**GT7 で何ができるか**

GT7 は運転支援を**個別に段階調整できる**。公式マニュアルの記述は、
TCS が「エンジン出力をどこまで使ってタイヤの空転を防ぐか」を設定する
ものであり、値を上げるほど空転が減る代わりにコーナー脱出速度が犠牲になる、
というもの。ABS はアンチロックの効き、カウンターステアアシストは
オーバーステアで振り出した車体を自動的に立て直す強さ、ASM
（Active Stability Management）はスピン防止で、on にすると速度を犠牲に
運転が易しくなる。プリセットは Beginner / Intermediate / Expert の3段階。
[索引: `manual/drivingoption/03`]

これらは**アップデートで挙動が変わる調整対象**である。
Update 1.31 の告知は、TCS の設定「1」で介入を弱め「5」で強めたこと、
ABS のフルブレーキ時の安定性を改善したこと、ASM のオーバーステア介入を
強めたこと、カウンターステアアシストの介入を弱めたことを明記している。
[本文: `news/00_1462138.html`]

**このプロジェクトにあるか**

**無い。** `FZN6DriverAssists` にあるのは自動変速だけ。

**入れるとしたら何が必要か**

実車データは**要らない。** ここが重要な分岐点である。

- ZN6 GT には実車に VSC / TRC が標準装備されているが、
  **その制御則（介入閾値、トルク削減量、ブレーキ配分）の出典は取れない。**
  メーカーは公開していない
- したがって「実車の VSC を再現した」とは**名乗れない**
- 一方、**操作の補助としてのアシストなら、出典は要らない。**
  `FZN6DriverAssists` のコメントが既にその立て付けになっている
  （「車両仕様ではなく、操作の補助」「ここの数値に出典は要らない
  （実車の制御ではないため）が、実車の挙動として語らないこと」）

**判定: 条件つきで入れる。**

必須条件は3つ。

1. **既定は全て off。** 検証は切った状態で行う（既存の作法と同じ）
2. 画面に「**運転補助であり、ZN6 の VSC/TRC ではない**」と出す
3. アシストを入れた状態のラップタイム・加速時間を
   `validation_targets` との比較に使わない

TCS は `Physics/driver.py` に既に実装がある（後輪スリップ率監視＋
スロットル制限）。**それを人間向けに転用するのが最短。**
ABS は `brake.py` に制動トルク配分があるので、車輪スリップ率で
トルクを落とす層を足すだけで足りる。

**優先度: 中。** FR のパワーオーバーステアは実車の性質であり、
それを消すアシストは「この車の挙動を隠す」方向に働く。
入れるが、**既定 off を絶対に崩さない。**

### 2.2 ドライビングライン表示 / ブレーキングインジケータ / コーンマーカー

**GT7 で何ができるか**

プリセットの説明に「Cone Marker/Driving Line assist」「Braking Indicator On」
が現れる。Beginner ではさらに Auto-Drive（ブレーキとステアの自動化）、
Intermediate では Auto-Drive（ブレーキのみ）が付く。
[索引: `manual/drivingoption/03`]

**このプロジェクトにあるか**

**無い。** ミニマップはあるが、路面上のラインは描いていない。

**入れるとしたら何が必要か**

実車データは**要らない。捏造にもならない。**

必要な入力は全て手元にある。

- コース中心線と曲率: `Tracks/track_catalogue.py`（数値で閉合を解いている）
- タイヤ摩擦係数と荷重感度: `vehicle.json`（`measured` / `estimated`）
- 制動能力: `brakes.max_brake_torque_total`

曲率と μ から「そのコーナーで出せる最大速度」が出て、そこから逆算して
ブレーキ開始点が出る。**これは物理計算であって、色を塗るだけの演出ではない。**

**判定: 入れる。**

ただし**表示の色は「モデルが出した限界」であって「実車の限界」ではない**
と明示すること。μ は `measured` だが荷重感度は `estimated` で、
そこに不確かさが乗る。HUD には既に信頼度表示の枠がある
（`FHudSnapshot::Confidence`）ので、そこに載せられる。

**優先度: 中〜高。** 実装が軽く、しかも**物理モデルの出力を目に見える形で
検証できる。** 「モデルの言う限界速度で走ると本当に曲がれるか」は
そのまま妥当性の点検になる。

### 2.3 MFD（走行中の設定変更）

**GT7 で何ができるか**

走行中に MFD からトラクションコントロールを調整できる
[索引: `manual/drivingoption/03`]。Fanatec の対応ホイールでは
左トグルが MFD のメニュー選択、右トグルが値の調整に割り当てられ、
スティックの LED が対応する MFD の色に光る
[索引: `manual/race/03` / `news/00_5548493.html` 系のアップデート告知]。

**このプロジェクトにあるか**

**無い。** セッティングはメニュー（停止中）でしか変えられない。

**判定: 条件つき。優先度: 低。**

走行中に変えられて意味があるのは、GT7 では燃料マップ・ブレーキバランス・
TCS である。このうち**燃料マップは §5.1 の理由で入れない。**
ブレーキバイアスと（入れるなら）TCS だけが対象になり、それだけのために
MFD を作るのは割に合わない。**セッティング項目が増えてから。**

## 3. 機能差分 — 記録・再生・視点

### 3.1 リプレイ

**GT7 で何ができるか**

リプレイの再生と保存がある。「Music Replay」は音楽に合わせてカメラ位置と
カットを自動生成する [本文: `products/gt7/`]。Sport モードの
オンラインタイムトライアル／予選タイムトライアルでランキングに
アップロードされた場合、Quick Menu から「Save Best Lap Replay」が使える
[索引: `manual/replay/01`]。

**このプロジェクトにあるか**

**無い。** ただし**素地は既にある。**

- 物理は**固定刻み 1ms（1000Hz）で決定的**
  （`FZN6FixedStepAccumulator`。描画フレーム時間で進めていない）
- テレメトリの CSV 記録は Python 側に実装済み（`Physics/telemetry.py`）

**入れるとしたら何が必要か**

実車データは**要らない。**

決定的である以上、**入力列（スロットル・ブレーキ・操舵・クラッチ・変速）を
固定刻みで記録すれば、再生時に同じ軌跡が完全に再現される。**
状態を毎フレーム保存する必要がない。1周 90 秒 × 1000Hz × 入力5軸 ×
float = 1.8MB 程度。圧縮も要らない。

注意点が2つ。

1. **再生時に描画フレームレートが変わっても結果が変わらないこと**を
   検査すること。ここが崩れるなら決定性が壊れている
2. **セッティングと車両データのハッシュを一緒に記録する。**
   `vehicle.json` が変わった後に古いリプレイを再生すると軌跡がずれる。
   黙ってずれるのが最悪なので、**不一致を検出して止めること**（憲法ルール6）

**判定: 入れる。優先度: 最高（§9 の1番）。**

理由は遊びではない。**これは検証の道具になる。**
同じ入力列を、セッティングを変えて再生すれば、
「車高を 20mm 下げると同じ操作でどう変わるか」を**入力の差を排除して**
比較できる。憲法ルール9 が禁じているのは「タイムだけを合わせる最適化」で
あって、入力を固定した比較はその逆——**原因を切り分ける手段**である。

### 3.2 ゴースト

**GT7 で何ができるか**

Arcade Time Trial と VR Time Trial にゴースト設定があり、
「Ghost Offset」でゴーストの表示を最大2秒まで 0.1 秒刻みで遅らせられる。
「Reset Sector」は読み込んだゴーストを各セクタで再スタートさせる
[索引: `manual/replay/01`]。

**このプロジェクトにあるか**

**無い。**

**入れるとしたら何が必要か**

**リプレイができれば、ゴーストはその副産物である。**
記録した軌跡を半透明の車体として描くだけ。新しい物理は要らない。

**判定: 入れる。優先度: 高（リプレイと同時。§9 の1番に含む）。**

### 3.3 フォトモード（Scapes / レースフォト）

**GT7 で何ができるか**

Scapes は世界2,500以上のロケーションで愛車を撮影できる機能で、
絞り・フォーカス・露出の調整と多数のフィルタを持つ。
Race Photo は走行中の自分を撮れる [本文: `products/gt7/`]。

**このプロジェクトにあるか**

**無い。** `-ZN6Shot=N`（N秒後に撮って終了）はあるが、これは
**開発者が自分の目で確認するための道具**であって、フォトモードではない。

**入れるとしたら何が必要か**

実車データは要らない。ただし **Scapes 相当は入れられない。**
2,500 の実写ロケーションは、**写真のライセンスの問題**である
（`PHASE15_DATA_LICENCE.md` が標高データについて避けたのと同じ問題を
画像で起こす。`SPEC_PHASE2_BACKLOG.md` §2.2 が既にこれを指摘している）。

自前のコース上で時間を止めて自由カメラを回すだけなら、
UE の機能で安価に作れる。

**判定: 条件つき（自前コース内のみ）。実写背景は入れない。優先度: 低。**

視覚層なので、評価オラクルは見る人の主観でよい
（`AGENT_TOPOLOGY.md` §4）。ただし**今の見た目（VFX ほぼ無し、
縁石も無し）で写真を撮る機能を先に作っても、撮るものが無い。**
順序として煙・縁石・環境光が先。

### 3.4 車内視点 / ボンネット視点 / カメラ切り替え

**GT7 で何ができるか**

R1 ボタンで視点を切り替える。用意されているのは
'Cockpit View' / 'Normal View' / 'Bonnet View' / 'Chase View'
[索引: `manual/race/03`]。

**このプロジェクトにあるか**

**チェイスカメラ1つだけ。** `ZN6VehicleActor.cpp` の
`CameraBoom`（TargetArmLength 750cm、SocketOffset Z=220cm）と
`ChaseCamera` しかない。

**入れるとしたら何が必要か**

**実車データは、視点の位置についてだけ必要になる。**

- ボンネット視点・チェイス視点: **要らない。** 演出上の位置でよい
- **車内視点は、要る。** 目線位置（アイポイント）は実車の寸法であり、
  適当に置くと「ZN6 の車内から見た景色」を名乗れない。
  `vehicle.json` に**アイポイントの項目は無い**（`dimensions` にあるのは
  全長・全幅・ルーフ高・ホイールベース・トレッド・最低地上高・最小回転半径）

  → 目線位置の出典が取れないなら、**`assumed` として明示し、
  「ZN6 のアイポイントではない」と画面に書く。**
  埋めずに `unknown` のまま演出値を使うのが憲法ルール1に沿った扱い

- 内装メッシュ: 導入済みの CC-BY モデルに内装があるかは**未確認。**
  無ければ車内視点は「宙に浮いた視点」になる

**判定: 入れる（ボンネット/チェイス/自由）。車内視点は条件つき。
優先度: 高（§9 の3番）。**

視点を増やすことには、遊び以外の理由がある。
**荷重移動によるロールとピッチは既にモデルが出しており
（`FZN6BodyAttitudeFeel` 経由で車体を傾けている）、
車内視点はそれを最も鋭く見せる。** 今のチェイスカメラは
`bInheritPitch = false` / `bInheritRoll = false` で車体の姿勢を
受け取っておらず、**モデルが計算した姿勢変化が画面にほとんど出ていない。**

### 3.5 ミラー / バックカメラ

**GT7 で何ができるか**

**確認できなかった。** ルームミラー表示の on/off や、リアビューの
切り替えを説明した公式ページに到達していない（§8）。
車内視点にミラーが描かれること自体は製品映像から明らかだが、
**映像は出典として扱わない**（憲法ルール2）。

**このプロジェクトにあるか**

**無い。**

**入れるとしたら何が必要か**

実車データは要らない（ミラーの位置は内装メッシュに従う）。
技術的には SceneCapture2D をもう1つ回すことになり、
**描画コストが素直に倍近く乗る。**

**判定: 条件つき。優先度: 低。**
対戦相手が居ない現状では、**後ろを見る理由が無い。**
AI 対戦（§6.1）を入れるまで保留。

## 4. 機能差分 — 見た目とカスタマイズ

### 4.1 ライブリーエディタ

**GT7 で何ができるか**

Livery Editor でペイントとデザインを施せる [本文: `products/gt7/`]
[索引: `manual/liveryeditor/01`]。

**このプロジェクトにあるか**

**9色の単色のみ**（`UI/ZN6Livery.h`）。デカール・レイヤーは無い。
`MI_Default_Blend` の `BaseColorFactor` を `UMaterialInstanceDynamic` で
差し替える実装で、塗装スロットは色相で判定している
（`ZN6::IsPaintSlot()`）。

**入れるとしたら何が必要か**

実車データは要らない。**ただし2つの落とし穴がある。**

1. **純正色を名乗れない。** ZN6 の純正カラーコードと名称の出典が
   取れていないことは既に記録済み（`HANDOFF_NEXT_SESSION.md` §1.3）。
   「クリスタルホワイトパール」等を勝手に付けない
2. **実在ブランドのロゴ・実在チームのカラーリングを入れない。**
   商標の問題であり、`PHASE15_DATA_LICENCE.md` が地図データについて
   下した判断と同じ理由で、**置いたうえで出典を書き忘れるほうが
   取り返しがつかない**

**判定: 条件つき（自作の図形のみ）。優先度: 低。**
物理的整合性に一切寄与しない。9色で足りている。

### 4.2 GT Auto 相当（ホイール・エアロ・ワイドボディ・ロールケージ）

**GT7 で何ができるか**

130種以上のホイールデザイン、650種以上のエアロパーツ、
一部車種でロールケージ追加とワイドボディ化 [本文: `products/gt7/`]。

**このプロジェクトにあるか**

**無い。**

**判定: 入れない。**

理由は §5.2 のチューニングと同じ。**外装パーツは見た目だけの話ではない。**
エアロパーツを付けたら Cd と揚力係数が変わるはずだが、

- `aerodynamics.cd` は `official_marketing`（0.27、min 0.27 / max 0.30）で
  **純正状態の値しかない**
- `lift_coefficient_front` / `_rear` は **`unknown`**

つまり**純正のダウンフォースすら計算できていない。**
社外エアロの係数を置けば、それは100%の捏造である（憲法ルール1）。

「見た目だけ変えて物理は変えない」なら成立するが、
それは**「エアロを付けても何も起きない」という物理的に誤った状態**を
作ることになる。`Physics/setup.py` の `aero_downforce` が既に
同じ理由で `UNSUPPORTED` に入っている。**同じ判断を外装にも適用する。**

### 4.3 縁石・VFX（煙・水しぶき・火花）

**GT7 で何ができるか**

雨天では水たまりができ、走行ラインから先に乾く [本文: `products/gt7/`]。
（VFX 単独の公式説明ページには到達していない。§8）

**このプロジェクトにあるか**

タイヤ痕のみ。**縁石は無い**（`HANDOFF_NEXT_SESSION.md` §2.2 B-4）。

**判定: 入れる（既に次セッションの作業として登録済み）。優先度: 中。**

**縁石は見た目だけの話ではない。**
縁石は路面高さの不連続であり、乗ると接地荷重が抜ける。
接地モデル（`Physics/ride.py`）と地形（`terrain.py`）が既にあるので、
**高さ場に縁石を入れれば物理が自然に反応する。**
「タイヤ痕」や「煙」より、こちらのほうが物理的に意味がある。

## 5. 機能差分 — 車両の状態変化（ここが最も「入れない」が多い）

### 5.1 燃料消費

**GT7 で何ができるか**

カスタムレース／ロビーで燃料消費を **x1〜x50** に設定できる。
有効にすると、ピットストップでゴールまたは次のピットまでに必要な量を
給油し、給油メーターの下に残り距離が表示される
[索引: `manual/race/07` / `manual/worldcircuit/08`]。

**このプロジェクトにあるか**

**無い。** `vehicle.json` に `fuel.tank_capacity` = 50 L（`official`）は
あるが、**消費を計算する材料が無い。**

**入れるとしたら何が必要か**

**実車データが要る。取れない。**

燃料消費率を出すには**正味燃料消費率（BSFC）マップ**——回転数と負荷の
2次元で g/kWh を与える表——が要る。FA20 の BSFC マップは**公開されていない。**
`Physics/engine.py` が持っているのはトルクカーブだけで、
そこから燃料流量は出ない（同じトルクでも空燃比と熱効率で消費は変わる）。

「熱効率を一律 30% と置く」は**数値の捏造**である。
そして捏造の害は燃料計だけに留まらない。**燃料が減れば車重が減り、
車重が減れば加速も旋回も変わる。** 捏造した数値が
`validation_targets`（0-60mph 6.60〜7.60s の帯）との比較に流れ込む。

**判定: 入れない。**

> `fuel_consumption`:
> **`engine` に BSFC マップが無く、公開もされていない。**
> トルクカーブから燃料流量は導けない（同一トルクでも空燃比と熱効率で
> 変わる）。一律の熱効率を仮定すれば数値は出るが、それは捏造であり、
> **減った燃料ぶんの軽量化が加速性能の検証結果に混入する。**
> `fuel.tank_capacity`（50L / official）は残すが、消費はモデル化しない。

### 5.2 タイヤ消耗

**GT7 で何ができるか**

タイヤ消耗を **x1〜x50** に設定でき、ピットで交換される。画面左下に
タイヤ履歴が表示される。ゴールが近く状態が良ければ「Do Not Change」で
交換を省ける [索引: `manual/race/07`]。
Update 1.31 では**タイヤの発熱と摩耗のモデル**、および濡れ路面の
ハイドロプレーニングが最適化されている [本文: `news/00_1462138.html`]。

**このプロジェクトにあるか**

**無い。** `Physics/tire.py` に温度・摩耗の項は一切無い（grep で確認）。

**入れるとしたら何が必要か**

**実車データが要る。取れない。**

摩耗と発熱を入れるには、少なくとも

- 摩耗率とスリップ仕事・接地圧・温度の関係
- タイヤの熱容量と路面／空気への熱伝達
- **温度と μ の関係**（これが本体。摩耗より温度のほうが挙動を支配する）

が要る。`vehicle.json` の `tires.friction_coefficient` は
**単一の値**であり、温度依存の資料は無い。純正装着タイヤ
（`tires.oem_brand`）の温度—μ 特性をメーカーが公開することはない。

**判定: 入れない（現時点）。**

> `tyre_wear` / `tyre_temperature`:
> **`tires.friction_coefficient` は単一値で、温度依存の資料が無い。**
> 温度—μ 曲線を置けば数値は動くが、それは実車の特性ではない。
> **入れた瞬間、ラップタイムが「タイヤが温まったから」で説明可能になり、
> 物理モデルの誤差を吸収する自由パラメータになる**（憲法ルール9 が
> 最も警戒する形）。`Physics/setup.py` の `tyre_pressure` と同じ理由。

**例外の余地:** 「摩耗を入れる」ではなく「**スリップ仕事の積算を
テレメトリに出す**」なら、出典の要らない純粋な計算であり、
タイヤをどれだけ酷使したかの指標として意味がある。**そちらを推す。**

### 5.3 ピットストップ

**GT7 で何ができるか**

ピットロードに入ると自動制御に切り替わり、作業は決まった順序で行われる。
内容はタイヤ消耗・燃料消費・機械的ダメージの設定によって変わる
[索引: `manual/race/07`]。

**判定: 入れない（依存関係により無意味）。**

> `pit_stop`:
> **ピットで行う作業（給油・タイヤ交換・修復）が3つとも
> モデル化されていない**（§5.1 / §5.2 / §5.4）。
> 止まって数秒待つだけの演出になる。**先に入れるものが無い。**

### 5.4 ダメージモデル

**GT7 で何ができるか**

レース設定で Mechanical Damage を Light / Heavy に設定できる。
Update 1.20 / 1.25 で、ダメージが発生する衝突力の閾値と、
ダメージが車両性能に与える影響が変更されている
[索引: `manual/race/06` / `news/00_4319704.html` / `news/00_5705144.html`]。

**このプロジェクトにあるか**

**無い。** `Physics/obstacles.py` は法線方向の撃力だけを与え、
「与えないもの」として**車体の変形、部品の脱落**を明記している。

**入れるとしたら何が必要か**

**実車データが要る。取れない。**

車体変形には衝突エネルギー吸収特性（クラッシュボックスの荷重—変位曲線）が
要る。これはメーカーの CAE 資料であって、公開されていない。
「性能が何%落ちる」という数値にも根拠が無い。

**判定: 入れない。**

> `damage_model`:
> **車体の衝突エネルギー吸収特性が非公開。**
> 「ぶつけたら出力が 10% 落ちる」の 10% に出典が無い。
> `obstacles.py` が既に「与えないもの」として変形と脱落を挙げており、
> その判断をここでも維持する。
> **視覚的な傷（テクスチャ）だけを入れるのも避ける。**
> 性能が変わらないのに壊れて見えるのは、物理と表示の不一致であり、
> 憲法ルール4 の精神（分離はするが、嘘はつかない）に反する。

### 5.5 天候・時間の変化

**GT7 で何ができるか**

時間と天候の推移は、**各コースの実在地点の気候データに基づく
シミュレーションモデル**で動く。夜に始まって朝日の中でゴールする、
といった連続的な変化が起こる。路面が濡れて乾く過程も詳細に模擬され、
低い場所に水たまりができ、車が水をかき分ける走行ラインから先に乾く。
**降雨レーダー**があり、長いレースの戦略を立てられる。
路面温度がタイヤのグリップに影響する [本文: `products/gt7/`]
[索引: `manual/race/04`]。

**このプロジェクトにあるか**

**無い。** 常に晴れ・固定光。

**入れるとしたら何が必要か**

ここは**視覚と物理を分けて判定する。**

| 要素 | 実車データ | 判定 |
|---|---|---|
| 時間の変化（太陽高度） | **要らない。** 天文計算で出る | **入れてよい。優先度 低〜中** |
| 気候データに基づく天候推移 | 実在地点の気象データが要る | **入れない。** コースが架空なので、そもそも対応する地点が無い |
| 雨の見た目（雨粒・反射・水しぶき） | 要らない | 条件つき。視覚層 |
| **濡れ路面の μ** | **要る。取れない** | **下記** |
| 路面温度→グリップ | 要る。取れない | 入れない |
| 降雨レーダー | 天候モデルの副産物 | 天候モデルが無いので無意味 |

**濡れμの扱いが核心。**
`HANDOFF_NEXT_SESSION.md` §2.2 D は既にこう指示している——
「タイヤの μ が濡れでどう変わるかの**出典が無い。** `assumed` として明示し、
それを使った結果は検証に使えないことを画面にも出す」。

**判定: 時間変化のみ入れる。雨は条件つき（`assumed` 明示・検証禁止）。
気候モデルと路面温度は入れない。優先度: 中（依頼者の要望にあるため）。**

**乾燥時の結果がビット単位で変わらないこと**を検査で担保すること
（`Physics/setup.py` の `CarSetup()` 中立時と同じ作法）。

## 6. 機能差分 — 対戦・オンライン・進行

### 6.1 AI 対戦

**GT7 で何ができるか**

PS5 版には **GT Sophy**（Polyphony Digital と Sony AI が共同開発した
強化学習ベースの AI）が搭載されている。Sophy 2.0 は 2023年11月2日の
Spec II で提供され、9コース・340台に対応した
[索引: `news/00_4176595.html`]。
Sophy 2.1 は **2025年3月27日の Update 1.57**（PS5 専用）でカスタムレースに
対応し、ライバル車ごとに Sophy を選べるようになった。タイヤ消耗・燃料消費の
設定も調整でき、自分のガレージの車でワンメイクレースを組める。
対応は19コース（アメリカ5・ヨーロッパ10・アジアオセアニア4）
[本文: `news/00_4957003.html`]。

**このプロジェクトにあるか**

**対戦相手はいない。** ただし **`Physics/driver.py` に PID ベースの
AIドライバーが既にある**（Pure Pursuit 操舵 + トラクションコントロール +
スピン検出 + カウンターステア）。UE 側にはまだ移植されていない。

**入れるとしたら何が必要か**

実車データは**要らない。**車は1台しかないので**ワンメイクにしかならないが、
それは欠点ではない。同じ車・同じ物理で複数台を走らせることになるので、
BOP も PP も要らず、データの捏造もゼロ。**

必要なのは、

1. `driver.py` の C++ 移植（`ZN6Vehicle.cpp` が Python から移植された
   のと同じ作業。前例がある）
2. **N 台ぶんの物理を 1000Hz で回す負荷の検証。**
   現在 1台で 1ms 固定刻み、`MaxStepsPerFrame = 200`。
   4台にすれば単純に4倍。**間に合わなければ `DroppedS` が増えるので、
   それを黙って捨てずに検出すること**（既に計測用フィールドがある）
3. 車同士の当たり判定。`obstacles.py` は円柱と長方形の判定なので、
   **長方形同士に拡張が要る。** かつ「車体同士の摩擦係数に出典が無い」
   という同じ問題が起きる。法線撃力だけに留めるのが一貫している

**強化学習は入れない。** Sophy は Sony AI の研究成果であり、
このプロジェクトで同等のものを作る話にはならない。
**PID + Pure Pursuit で「事故らず1周する」までが目標**という
`driver.py` の立て付けを変えない。

**判定: 入れる（ワンメイクのみ）。優先度: 中〜高。**
「ゲームとして遊べるか 25点中2点」（`HANDOFF_NEXT_SESSION.md` §0.6）の
最大要因が「対戦相手がいない」であり、**ここは実車データを一切必要と
しないまま埋められる、数少ない大穴。**

### 6.2 オンライン対戦（Sport Mode / ロビー）

**GT7 で何ができるか**

Sport Mode でデイリーレースや公式オンラインチャンピオンシップに参加できる
[本文: `products/gt7/`]。Driver Rating（DR）と Sportsmanship Rating（SR）が
あり、接触には DR へのペナルティとタイムペナルティが科される。
ペナルティを消化せずに走り続けると追加される。接触やショートカットが
積み重なると失格になりうる。意図的な妨害は即時ペナルティ
[索引: `manual/sportmode/01` / `news/00_4914793.html`]。

**判定: 入れない。**

> `online_multiplayer`:
> **このプロジェクトの目的（物理的整合性）に一切寄与しない。**
> かつ実装量が突出して大きい（サーバ、認証、ネットワーク同期、
> 不正対策、レーティング、ペナルティ判定）。
> **ネットワーク同期は物理の決定性と正面から衝突する。**
> 今の 1ms 固定刻み・単一シミュレーションという構造は、
> ロールバックや補間を入れた瞬間に「再現する」性質を失う。
> **リプレイ（§3.1）が成立する前提そのものを壊す。**

**ローカルのタイムランキング**（自分の記録の蓄積）は別で、
リプレイ／ゴーストの副産物として安価に作れる。そちらは入れてよい。

### 6.3 BOP（Balance of Performance）

**GT7 で何ができるか**

BOP はレース車両の性能を均衡させ、オンラインで公平な勝負を成立させる仕組み
[索引: `gtsport/news/bop_update.html` 系 / `manual/worldcircuit/08`]。

**判定: 入れない。**

> `balance_of_performance`:
> **車が1台しかない。均衡させる対象が存在しない。**
> かつ BOP は「実車の性能を意図的に歪めて競技を成立させる」仕組みであり、
> **このプロジェクトの目的（実車の挙動を再現する）と正面から反する。**
> 仮に将来 BRZ を足しても、ZN6 と BRZ の差を人為的に消すことは
> デジタルツインではない。

### 6.4 進行と報酬（GT Café / ライセンス / クレジット）

**GT7 で何ができるか**

GT Café のメニューブックを進めながら車を集める。メニューブックには
コレクターレベルの条件がある（例: No.43 は Lv.33 以上、No.44 は Lv.35 以上）。
ライセンスセンターがあり、ノーマルライセンス完了後に Master Licenses が
解放される。少額の資金から中古車を買い、レースでクレジットを稼ぎ、
チューンするか新車を買って次に進む [索引: `manual/cafe/01` / `products/gt7/`]。

**判定: 入れない。ただし一部は別物として入れる。**

> `career_progression` / `credits` / `car_collection`:
> **車が1台しかないので「集める」も「買う」も成立しない。**
> クレジットで買えるパーツも入れない（§4.2 / §5 の理由）。
> **報酬でプレイヤーの行動を誘導する仕組みは、
> 物理的整合性の検証に何も寄与しない。**

**別物として入れるべきもの:**

- **ライセンス試験に相当するもの**（区間ごとの目標タイム、
  「このコーナーを X km/h 以上で抜ける」等）は、
  **物理モデルが出した限界値を目標にできる**ので、
  §2.2 のドライビングラインと同じく**モデルの妥当性点検になる。**
  進行や報酬を付けず、練習課題として置くなら意味がある
- **コース選択 UI** は進行システムではなく、単に足りていない機能
  （`HANDOFF_NEXT_SESSION.md` §2.2 C）。4本あるのに
  `-ZN6Track=` かレベル直開きでしか選べない。**これは入れる**

### 6.5 ペナルティ / トラックリミット判定

**GT7 で何ができるか**

トラックリミット違反でペナルティが科される。ペナルティは通常タイムロスの
形で科され、各コースにはペナルティ消化のために自動減速する区間がある
[索引: `manual/sportmode/01` / `news/00_4914793.html`]。

**このプロジェクトにあるか**

**判定だけある。** `FHudSnapshot` に `bOffTrack` と `bLapInvalidated` が
あり、コース外はラップ無効として扱っている。**タイムペナルティは無い。**

**判定: 現状で足りている。優先度: 低。**
1人で走るのにタイムペナルティを科す意味は薄い。
AI 対戦（§6.1）を入れてから再考。

## 7. 機能差分 — 入力機器

### 7.1 ステアリングホイールと Force Feedback

**GT7 で何ができるか**

複数メーカーのホイールに対応し、**FFB の挙動はアップデートで調整される
対象**である。Thrustmaster T-GT、FANATEC Podium、FANATEC GT DD Pro に
ついて、暫定対応として FFB とトルク強度を大きく下げた告知がある
[索引: `news/00_4085673.html`]。
Logitech G923 では **TRUEFORCE** を使い、エンジン振動とホイールスピンの
振動を再現している [索引: `news/00_4317998.html`]。
Fanatec との協業で公式ダイレクトドライブホイール
「Gran Turismo DD Extreme」（15Nm ClubSport DD+ ベース）が出ている
[索引: `news/00_8965884.html`]。
DualSense のハプティックフィードバックとアダプティブトリガーにも対応
[本文: `products/gt7/`]。

**このプロジェクトにあるか**

**キーボードのみ。** `DefaultInput.ini` の軸は W/S/A/D/LeftShift/SpaceBar と
矢印キーだけ。ゲームパッドの軸割り当ても無い。

**入れるとしたら何が必要か**

**ここは2つに割って判定する。割らないと間違える。**

**(a) アナログ入力（パッド／ホイールの軸を読む）**

実車データは**要らない。** そしてこれは**物理的に重要**である。

- `FZN6DriverFeel` の平滑化（`SteerRateRadPerS` 1.1、
  `SteerSpeedFalloffPerMps` 0.045 等）は**キーボードのために存在する。**
  ヘッダに「キーボードは 0 か 1 しか出せない」「これは操作系の補助であって
  車の特性ではない」と明記されている
- **アナログ入力にこれを掛けると、人間の入力を歪める。**
  `HANDOFF_NEXT_SESSION.md` §2.2 E が既に指摘している
- 高速で舵角を絞る処理は、**アナログ入力では有害。**
  実車のステアリングギア比は一定である

**(b) Force Feedback（ホイールに力を返す）**

**実車データが要る。取れない。**

FFB の力の正体は**セルフアライニングトルク**（タイヤの接地面で生じ、
キングピン軸まわりに戻ろうとするモーメント）である。これを物理的に
出すには、

- タイヤのニューマチックトレール（`vehicle.json` に無い）
- **キャスター角とキングピン軸の幾何**
  → `suspension.geometry` が **`unknown`**
- ステアリングギア比とラック効率

が要る。`Physics/setup.py` の `UNSUPPORTED` は既に
`caster` について「suspension.geometry が unknown。キャスターから
キャンバー変化や**セルフアライニングトルク**を出せない」と書いている。
**FFB はこの `caster` の項目と全く同じ壁に当たる。**

**判定:**
**(a) アナログ入力は入れる。優先度: 高（§9 の2番）。**
**(b) FFB は条件つき。** 演出として出すなら、
「これは ZN6 の操舵反力ではない」と明示し、
`vehicle.json` に混ぜず `Audio/audio.json` と同じ扱いで
**別ファイルに `assumed` として置く**（憲法ルール18）。

> `force_feedback_physical`:
> **`suspension.geometry` が `unknown` で、セルフアライニングトルクを
> 導けない**（`Physics/setup.py` の `caster` と同じ根拠）。
> 横力と荷重から「それらしい」力を作ることはできるが、
> それは ZN6 の操舵反力ではない。**演出として出す場合は
> `vehicle.json` の外に置き、実車の反力として語らない。**

**さらに検証できない問題がある。** 実機が無い
（`HANDOFF_NEXT_SESSION.md` §2.2 E）。
**「実装した」と「動く」は別**である（§0.1 の事故と同型）。
デバイスを持っていない以上、**どこまでが確認済みでどこからが未検証かを
必ず区別して書くこと。**

### 7.2 H パターンシフター

**GT7 で何ができるか**

**確認できなかった**（§8）。対応ホイール／シフターの一覧を示す公式ページに
到達していない。

**このプロジェクトにあるか**

**無い。** 変速は `ZN6_ShiftUp` / `ZN6_ShiftDown`（E / Q）の**相対変速。**

**入れるとしたら何が必要か**

実車データは要らない。**ただし構造の変更が要る。**
H パターンは**絶対位置**（今 3速に入っている、を直接指定する）であり、
相対変速の実装とは噛み合わない
（`HANDOFF_NEXT_SESSION.md` §2.2 E が指摘済み）。

`Physics/clutch.py` があるので、**クラッチを踏まずにギアを入れる**
といった実車的な失敗も表現できる余地がある。

**判定: 入れる（アナログ入力と同時）。優先度: 中。**

## 9. 次に実装すべき3つ

判定基準は**このプロジェクトの目的（物理的整合性）への寄与**であって、
GT7 との見た目の近さではない。

実装量の見積は、既存コードの規模から出した目安である。
**実測ではないので、そのまま工数として扱わないこと。**

---

### 1位: 決定的リプレイ + ゴースト

**なぜ最初か**

**遊びの機能である以上に、検証の道具だからである。**

物理は 1ms 固定刻みで決定的に回っている（`FZN6FixedStepAccumulator`。
「描画のフレーム時間で物理を進めない。フレームレートが変われば結果が
変わってしまい、再現性が無くなる」）。
**この性質は既に手に入っているのに、まだ何にも使われていない。**

入力列を記録して再生すれば、

- **同じ操作で、セッティングだけを変えた比較ができる。**
  今は「車高を下げたら速くなったのか、運転が良かったのか」を分離できない
- 接地力をタイヤに繋いだ影響（`bRideDrivesTyreLoads`。§1.4 で
  「入れるとラップタイムが変わる」と記録されている）を、
  **同一入力で定量化できる**
- 積分が1次であることによる刻み依存（issue #28: 発進2秒後の速度が
  2.49〜4.43 m/s と動く）を、**再現可能な形で示せる**

憲法ルール9 が禁じるのは「タイムだけを合わせる最適化」であって、
**入力を固定した比較はその逆——原因を切り分ける手段**である。

ゴーストは同じ記録を半透明で描くだけなので、実質同じ作業に含まれる。

**必要な実車データ: 無し。**

**実装量の見積: 中。**

| 作業 | 目安 |
|---|---|
| 入力列の記録・保存（バイナリ or CSV） | 200〜300 行 |
| 再生時の入力差し替え（`ControlInput` の供給元を切り替える） | 100 行程度 |
| `vehicle.json` / セッティングのハッシュ照合と**不一致の検出** | 100 行程度 |
| ゴースト車体の描画（既存メッシュの半透明複製） | 150 行程度 |
| 再生カメラ（既存のチェイスを流用） | 小 |
| 検査（**同じ記録が同じ軌跡を出す。描画 fps を変えても変わらない**） | 10〜15 件 |

**落とし穴:** 浮動小数の非決定性。UE のビルド設定（高速数学）で
再生がずれるなら、それは**リプレイの不具合ではなく物理の決定性の
不具合**である。黙って許容せず、issue にすること（憲法ルール6）。

---

### 2位: アナログ入力（ゲームパッド / ホイールの軸）と、キーボード補助の分離

**なぜ2番目か**

**入力の質は、挙動評価の前提だからである。**

今はキーボードしか無く、そのために `FZN6DriverFeel` が
入力を大きく加工している——操舵は 1.1 rad/s でしか動かず、
速度が上がると最大舵角を 0.045/(m/s) で絞る。
ヘッダ自身が「**これは操作系の補助であって、車の特性ではない**」と
書いている。

**つまり今、人間が触っている車は、モデルが計算している車とは
別の何かである。** この状態で「挙動が実車らしいか」を主観評価しても、
何を評価しているのか分からない。

さらに、`HANDOFF_NEXT_SESSION.md` §0.2 が指摘した失敗
（「動いているゲームを一度も見ていなかった」）の運転版がここにある。
**モデルの過渡応答を人間が感じ取るには、連続量の入力が要る。**

**FFB はここに含めない**（§7.1 の (b)）。
`suspension.geometry` が `unknown` である以上、
セルフアライニングトルクは出せない。**分けて考えることが判断の本体。**

**必要な実車データ: 無し**（軸を読むだけ）。

**実装量の見積: 小〜中。**

| 作業 | 目安 |
|---|---|
| `DefaultInput.ini` に軸を追加（パッドのトリガー・スティック、汎用ホイール軸） | 設定のみ |
| **デバイス種別で `FZN6DriverFeel` を切り替える**（アナログなら平滑化と舵角絞りを外す） | 100〜150 行 |
| デッドゾーン・入力カーブの設定項目（**演出値として明示**） | 100 行程度 |
| H パターン（絶対位置指定の変速）への対応 | 100〜150 行 |
| 検査（キーボードでの既存挙動が**ビット単位で変わらないこと**） | 5〜8 件 |

**落とし穴:** **実機が無い。**
`HANDOFF_NEXT_SESSION.md` §2.2 E のとおり、PS5 コントローラも T300RS も
手元に無い。**「対応した」と書かないこと。**
「軸を読む経路を作った。実機での確認は未実施」と書くこと。
これは §0.1 で起きた「操作できないメニューを入れたと報告した」事故の
再発防止そのものである。

---

### 3位: 視点の追加（車内 / ボンネット / 自由）と、カメラへの車体姿勢の反映

**なぜ3番目か**

**モデルが計算している荷重移動が、今ほとんど画面に出ていないからである。**

`FZN6BodyAttitudeFeel` は横1Gあたり 4.5度、前後1Gあたり 2.6度 だけ
車体を傾けている。ところがカメラは
`bInheritPitch = false` / `bInheritRoll = false` で、
**その姿勢変化を受け取っていない。**
750cm 後方・220cm 上方の固定チェイスから見ているので、
**ロールもピッチも、ほとんど見えない。**

このプロジェクトの中核的な成果——加速時に荷重が後輪に乗る、
FR だからパワーオーバーステアが出る——は、**荷重移動の可視化なしには
伝わらない。** 視点はその表示装置である。

`Docs/AGENT_TOPOLOGY.md` §4 のとおり、ここは**視覚層なので評価オラクルは
見る人の主観**であり、「良く見えるまで回してよい」層である。
ただし §0.7 の教訓に従い、**必ず自分で撮って、自分の目で見ること。**

**必要な実車データ: 車内視点のアイポイントのみ。取れない。**
→ `assumed` として置き、**「ZN6 のアイポイントではない」と画面に出す。**
出典が取れるまで、車内視点は「暫定」と明示する。

**実装量の見積: 小。**

| 作業 | 目安 |
|---|---|
| カメラを複数持ち、キーで切り替える（`ZN6_ChangeView`） | 100 行程度 |
| ボンネット視点・自由視点（既存 SpringArm の設定違い） | 50 行程度 |
| **車体姿勢（ロール/ピッチ）をカメラへ伝える**経路 | 50 行程度 |
| 車内視点（内装メッシュの有無を**先に確認する**） | 未定。内装が無ければ保留 |
| 検査（**視点を変えても物理の結果がビット単位で変わらないこと**） | 3〜5 件 |

**落とし穴:** 導入済みの CC-BY モデルに内装があるかを**確認していない。**
無ければ車内視点は宙に浮く。**先に確認してから着手すること。**
