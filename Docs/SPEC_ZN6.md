## 1. プロジェクト基本定義

### 1.1 最終目的

実車の外観・寸法・エンジン特性・駆動系・タイヤ・サスペンション・重量配分・空力・路面・車両運動を、公開情報と物理モデルを利用して可能な限り再現するレーシングシミュレーターの構築。

「見た目がリアル」であることを最終目的とせず、視覚・音響・車両挙動・タイヤ・加減速・旋回・荷重移動・機関系を個別に検証・統合した物理的整合性をゴールとする。

### 1.2 前提条件（固定）

- 家から一歩も出ない（実車スキャン・実車録音・実測なし）。
- 可能な限り無料のソフト・AIサービスを使用する。
- AIに調査・コード生成・テスト・分析を担当させる。
- **最初のターゲット車両は「トヨタ86（ZN6）前期 GT 6MT 日本仕様」1台に限定する。**
- **AIが推測した数値と、資料から確認できた数値を絶対に混同しない。**
- 完全自動ではなく「無料枠を最大限利用し、ローカルの Python で自動検証する」設計とする。

**段階的に導入するもの（Phase 1 では入れない）**

| ツール | 導入時期 | 理由 |
|---|---|---|
| Unreal Engine 5 | **Phase 8** | 第1完成目標に不要。インストールと初回シェーダーコンパイルのコストが大きい |
| Blender | **Phase 11** | 同上。導入時も GUI ではなく `pip install bpy` でモジュールとして扱う |
| Tripo AI | **Phase 10** | Phase 2 バックログ |

### 1.3 基準車両

**トヨタ86 前期型 GT グレード 6MT 日本仕様（DBA-ZN6-D2E8）**

| 項目 | 決定 |
|---|---|
| 世代 | 前期（2012年4月〜2016年8月マイナーチェンジ前） |
| グレード | GT（トルセンLSD標準、ファイナル 4.100） |
| ミッション | 6MT |
| 仕向地 | 日本仕様（JIS ネット値） |
| 駆動方式 | FR |
| エンジン | FA20（水平対向4気筒 1,998cc） |

選定理由は `Docs/ZN6_BASELINE.md`。一次資料は `Vehicles/ZN6/References/86_spec_201502.pdf`（トヨタ公式 主要諸元表 2015年2月版）。

**基準車両を変更する場合は `vehicle.json` を作り直すこと。** ギア比・ファイナル・車重・装備が連動して変わるため、部分的な差し替えは不整合を生む。

## 2. 人間とAIの役割分担

### 2.1 人間が行う作業（最小限）

- PCおよび必要ソフトのインストール・環境構築。
- GitHubリポジトリの作成と可視性の管理。
- AIが提案する最終的な仕様・変更の承認または却下。
- （Phase 10 以降）公開画像の収集と Tripo AI への入力。

### 2.2 「作るAI」と「疑うAI」の分離

**詳細は `Docs/AGENT_TOPOLOGY.md`。ここでは仕様として確定した点のみ書く。**

元仕様書 §2.2 は7ロールをフラットな箇条書きで並べるだけで、**誰が誰の下流にいるか**が
書かれていなかった。以下のトポロジを正とする。

```
                 PROJECT MANAGER
                        │
           ┌────────────┼────────────┐
           ↓            ↓            ↓
       Research      Physics         3D
          AI            AI           AI
           │            │            │
           └────────────┼────────────┘
                        ↓
                    Validator          ← 疑うAI
                        ↓
                    Optimizer
                        ↓
                      QA AI
```

#### 確定事項

1. **Validator は producer 全ての下流に置く。作った本人が採点しない。**
2. **Optimizer は Validator の発見にのみ反応する。** 自発的にパラメータを触らない。権限は Level 2〜3
3. **producer は自分の出力を承認できない。Validator は修正できない。** この非対称性が構造の全て
4. **`vehicle.json` の書き手は Research 1つに限る。** 他は読むだけ。Optimizer は変更案を別ファイルに出す
5. **横並びは依存関係であって、実行の並列を要求しない**

#### `HANDOFF.md` §6 の2画面分担との関係

**2画面分担は、このトポロジを2つの面に畳んだ最小実装。置き換えではない。**

| ロール | 現在の実装 |
|---|---|
| PROJECT MANAGER | 人間 |
| Research | チャット（claude.ai） |
| Physics / QA | Claude Code |
| **Validator** | **チャット（claude.ai） + 層1フック** |
| 3D / Optimizer | 未稼働（Phase 10 / 17〜） |

**Validator が Physics と別の面にいる**ため下流関係は保たれている。
producer が Physics 1つしかない Phase 4〜8 の段階でロールを7つに割っても、
オーバーヘッドだけが増える。**段階的に増やす**（`AGENT_TOPOLOGY.md` §6）。

#### 分離を担保しているもの

**同一コンテキストで自己検算させても意味がない。** producer は自分の出力を作るときの
前提をそのまま持っているため、同じ前提で採点しても前提の誤りは検出できない。
検出できるのは計算ミスだけで、**このプロジェクトで怖いのは前提の誤り**である。

分離の強さは実装手段によって違う。

| 手段 | 強さ |
|---|---|
| **コミット前フック** | **最強。** コンテキストを持たないので説得できない |
| 別セッション / 別画面 | 強。前提を共有しない |
| **同一セッションのサブエージェント** | **弱。** プロンプト経由で親の前提が流れる |

サブエージェントで Validator を実装する場合、**プロンプトに結論を書かないこと。**
渡すのは一次資料へのパス、判定基準、出力形式だけ。

### 2.3 評価のオラクルは層によって違う

**「評価担当AIが100点を出すまで修正を繰り返す」ループは、視覚層でのみ使う。**

| 層 | オラクル（正解を決めるもの） | 収束まで回してよいか |
|---|---|---|
| **視覚** | **評価者の主観そのもの** | **○** |
| 音響 | 主観 + 実車動画との突き合わせ | △ 条件付き |
| **物理** | **実測値の範囲と保存則** | **✗ 禁止** |
| **データ** | **一次資料。それだけ** | **✗ 論外** |

つやや背景の作り込みに客観的な正解は無く、**「良く見えるか」が正解**なので、
評価者の主観がオラクルとして正しい。だから収束まで回してよい。

物理は違う。**0-100km/h の正解は実測値であって、評価者のスコアではない。**
スコアを上げるループを回すと、実車から離れてもスコアが上がりうる。
これは §5.1 のルール9「ラップタイムだけを合わせる最適化の禁止」そのもの。

**したがって物理層の Validator は点数を付けない。**
「実測値の範囲に収まっているか / 保存則を破っていないか」の**二値**で答える。

§10.2 の Digital Twin Report のスコアは**最終報告であって最適化目標ではない。**
あのスコアを上げるために Optimizer を回してはいけない。

**これは §5.1 ルール6「物理計算と表示用3Dモデルを完全に分離する」の評価版である。**
分離されるのはモデルだけでなく、それぞれを何で採点するかも分離される。

## 5. 開発の憲法とデータ管理基準（最重要）

### 5.1 憲法の三層構造

元仕様書は18のルールを `AGENTS.md` 1枚に並べる想定だった。**これを性質別に3層へ分割する。**

理由: `CLAUDE.md` はコンテキストであって強制設定ではない。確実にブロックしたい項目はフックで実装しないと守られない。また1ファイルが長いほど遵守率が下がる。

| 層 | 場所 | 性質 | 読み込みタイミング |
|---|---|---|---|
| **層1** | `.claude/hooks/` | 機械的に検証できる。AIの判断に関係なく実行される | コミット時 |
| **層2** | `CLAUDE.md`（150行以内） | 判断を要する | 全セッション |
| **層3** | `.claude/rules/*.md` | パス限定。`paths` フロントマターでスコープ | 該当ファイルを触るときだけ |

**18ルールをどう三分類したか、その理由は `Docs/RULE_CLASSIFICATION.md` に記録してある。**

**仕様書全文を `CLAUDE.md` に入れないこと。** このファイル（`SPEC_ZN6.md`）は自動ロードせず、必要なときだけ読む。

#### 層1 が止めるもの

- **Level 0 パラメータの変更**（排気量・ホイールベース・公式ギア比・公式車重）
- `vehicle.json` のスキーマ違反（`source` / `confidence` / `unit` の欠落、非SI単位）
- pytest の失敗

### 5.2 データの信頼度と Confidence 設定

`vehicle.json` に記録するすべての数値は、以下の信頼度（`source`）と `confidence` 値を持つ。

**CL1版は4分類だったが、実データが `official_marketing` と `secondary` を必要としたため6分類に拡張する。**

| source | 定義 | confidence | 例 |
|---|---|---|---|
| `official` | メーカー公式の技術資料（諸元表・サービスマニュアル） | 0.90 – 1.0 | 車重 1,230kg、ギア比 |
| `official_marketing` | **メーカー公式だが販促資料。測定条件が明示されない** | 0.70 – 0.89 | 重心高 0.46m（「超低重心」の公表値） |
| `measured` | 第三者による実測（シャシダイ、計測器付きテスト） | 0.70 – 0.89 | 0-100km/h 実測 |
| `secondary` | **二次情報（専門誌・レビュー記事）。一次資料に当たれていない** | 0.70 – 0.89 | ステアリング径 0.365m |
| `estimated` | 物理モデル・幾何計算から推定 | 0.40 – 0.69 | タイヤ有効半径（サイズからの幾何計算） |
| `assumed` | AIによる仮定 | 0.0 – 0.39 | 出典が全く無い値 |

**`official_marketing` を `official` と分けた理由**: 販促資料の数値は測定条件（乗員・燃料の有無）が不明なため、公式であっても Level 0（変更禁止）に置けない。しかし `estimated` に落とすと探索範囲が不当に広がる。中間の階層が要る。

**`secondary` を `measured` と分けた理由**: 二次情報は実測かどうかが判別できない。confidence 帯は同じでも、**一次資料に当たれていない**ことを記録に残す必要がある。

#### confidence の帯は「上限だけ」を強制する

**帯を上に外れるのはエラー。下に外れるのは警告。**

防ぎたい事故は**過大申告**（`assumed` の値を confidence 0.9 で置く等）であって、
実際より慎重に申告することではない。帯の下限を強制すると、**正直な申告に嘘をつく圧力がかかる。**

`vehicle.json` に既にある実例:

| 項目 | source / confidence | 何を言っているか |
|---|---|---|
| `tires.size` | `secondary` / **0.6** | 二次情報で、**しかも一次資料と突き合わせられていない**（諸元表PDFにタイヤサイズの記載が無かった） |
| `brakes.rear_type` | `official` / **0.8** | 公式資料に載っているが、**グレード間の対応が曖昧** |

どちらも帯を下回るが、**記述として正しい。** 帯に合わせて 0.7 / 0.9 に上げると情報が失われる。
帯を下回る場合は `note` に理由を書くこと。

#### SI でない単位の扱い

内部計算は SI だが、`vehicle.json` は一次資料の表記に近い方が照合しやすい。
以下のみ例外として許容し、**変換が一意に定まること**を条件とする。

| 単位 | 用途 | 理由 |
|---|---|---|
| `L` | 排気量、燃料タンク容量 | 一次資料の標準表記。1 L = 1e-3 m³ で一意 |
| `persons` | 乗車定員 | 物理量ではなく個数。単位名を残す方が読み間違いを防げる |

**無条件に増やさないこと。** 追加するときは `Tools/validate_vehicle.py` の
`ACCEPTED_NON_SI_UNITS` に理由を書いて登録する。

#### 数値には unit を必須とし、文字列には課さない

`suspension.front_type` = `"マクファーソンストラット式コイルスプリング"` のような
**形式名は測定値ではない**ため `unit` を持たない。無次元の比（ギア比・圧縮比）は `"-"` を書く。

#### 単一値ではなく範囲を持たせる

```json
"cg_height": {
    "value": 0.46,
    "min": 0.44,
    "max": 0.48,
    "unit": "m",
    "source": "official_marketing",
    "method": "manufacturer_published_low_cg_claim",
    "confidence": 0.75,
    "note": "トヨタが「超低重心（重心高460mm）」として公表。出典が販促資料であり測定条件（乗員・燃料の有無）が不明。水平対向エンジン由来の特性で、直4と同じ初期値を置いてはいけない。"
}
```

#### 必須フィールド

| フィールド | 必須 | 備考 |
|---|---|---|
| `value` | ○ | 値が不明な場合はフィールド全体を文字列 `"unknown"` にする |
| `unit` | ○ | **SI単位**（m, kg, N·m, W, s）。無次元は `"-"` |
| `source` | ○ | 上表の6種のいずれか |
| `confidence` | ○ | `source` に対応する帯の中に収める |
| `min` / `max` | 推奨 | `official` 以外は原則付ける |
| `method` | `estimated` / `assumed` で必須 | 推定方法 |
| `note` | 任意 | 罠・制約・棄却した候補を書く |

**不明な値は `"unknown"` と書く。AIが勝手に実測値として補完しない。**

### 5.3 AIの変更権限

AIがラップタイムを合わせるために勝手に仕様を変更することを防ぐ。

| Level | 権限 | 対象 source | 例 |
|---|---|---|---|
| **Level 0** | **絶対変更禁止** | `official` | エンジン排気量、ホイールベース、公式ギア比、公式車重 |
| Level 1 | 限定的変更（範囲内のみ・理由必須） | `official_marketing` / `measured` / `secondary` | 空力係数、重量配分、重心高 |
| Level 2 | 探索可能 | `estimated` | タイヤμ、ダンパー、スプリング、ARB |
| Level 3 | 完全探索 | `assumed` | 詳細が全く不明なパラメータ |

#### Level 0 は「値」だけでなく「variant の選択」も保護する

**ZN6 のファイナルギア比は単一値ではない。**

| 仕様 | ファイナル |
|---|---|
| G 6MT（オープンデフ） | 3.727 |
| G 6MT（トルセンLSD オプション） | 4.100 |
| GT / GT"Limited" 全車 | **4.100** |
| 6AT 全車 | 4.100 |

`vehicle.json` の `transmission.final_drive.variants` に全パターンを記録してある。

**「ZN6のファイナルは4.100」と一括りにして G グレードのデータを引くと、約10%の駆動力誤差が入る。** これは 0-100km/h の検証で原因不明のズレとして現れ、Optimizer がタイヤμを不当に触って辻褄を合わせる典型的な事故につながる。

したがって層1のフックは、**`final_drive.value` と `final_drive.variants` の両方**の変更を検出して停止する。

## 6. 物理モデル構築パイプライン

物理エンジンは描画から独立させ、**Python で構築・検証しきってから** UE5（Phase 8）へ移す。

### 6.1 情報収集と優先順位

メーカー公式資料 > サービスマニュアル > 純正部品資料 > 専門誌 > 実測レビュー > オーナー測定 > 掲示板 > AI推定

収集項目の全体像は `Docs/DATA_COLLECTION_ZN6.md`（14カテゴリ）。

**ただし14カテゴリを最初から全部埋めない。物理モデルが実際に読む項目から育てる。** 何のために集めているかが分からなくなる作業を避けるため。

### 6.2 機関系（エンジン・駆動・ブレーキ）

#### エンジン

トルクカーブ（RPM vs Torque）を**複数のデータポイント**として収集し、スプライン補間する。Throttle、Friction、Inertia を考慮して出力トルクを計算する。

> **FA20 固有の警告**
> FA20 は **4,000rpm 付近にトルクの谷**があることが広く知られている。
> **最大出力点（7,000rpm）と最大トルク点（6,400〜6,600rpm）の2点だけで補間してはいけない。**
> この特性が完全に消え、加速シミュレーションで中回転域が実車より速くなる。
> そして**その誤差を Optimizer が別のパラメータ（タイヤμ等）で吸収してしまう。**
>
> シャシダイ実測（**ホイール出力ではなくエンジン軸換算**）を複数取得し、ばらつきを範囲として保持すること。
> 現在 `engine.torque_curve` は `unknown`。**最重要未収集項目。**

#### 駆動系（FR）

```
Throttle → Engine Torque → Clutch → Gearbox → Propeller Shaft
        → Final Drive / Differential → Drive Shaft → Rear Wheel
```

**CL1版（FF）との違い**: ギアボックスとファイナルの間に**プロペラシャフト**が入る。回転慣性の項が1つ増える。駆動輪は後輪。

#### ギア比

各ギアの比率、ファイナル、効率を定義する。ファイナルは §5.3 の variant に注意。

#### デファレンシャル（FR + トルセンLSD）

**基準車両の GT はトルセンLSDを標準装備する。** CL1版の「初期は Open Diff」という段階論は、ZN6 では実車と乖離する。

- 初期実装: Open Diff（比較基準として残す）
- **本番実装: トルセンLSD（Preload / Accel Lock / Decel Lock）**
- FR + LSD では、コーナー脱出時のパワーオンで**内輪から外輪へトルクが移り、オーバーステアを助長する**方向に働く。FF の「アンダーを消す」用途とは効き方が逆になる。

現在 `differential.preload` / `accel_lock_ratio` / `decel_lock_ratio` はいずれも `unknown`。

#### ブレーキ

Brake Torque、Wheel/Vehicle Speed、Tire Slip から計算し、後に ABS ロジックを統合する。

### 6.3 タイヤモデル（最重要：ブラックボックス化禁止）

Pacejka の係数を AI に適当に生成させない。「公開タイヤ情報 → サイズ・構造 → 一般的特性範囲 → 物理モデル → 不確実性範囲」のロジックで構築する。

- **段階的実装**: Fiala/Brush モデル（初期） → Magic Formula（中期） → Combined Slip 考慮（後期）
- **荷重感度**: 摩擦係数(μ)を固定せず、垂直荷重による特性変化をモデル化
- **キャンバー変化**: サスペンションストロークによるキャンバー変化が横力に与える影響を組み込む
- **候補探索**: AIは正解を当てるのではなく、妥当なパラメータセット（TireModel_A, B, C）から矛盾の少ない領域を探索する

> **FR での Combined Slip の扱い（CL1版からの変更）**
> FF では駆動と操舵が前輪に集中するため、複合スリップは前輪の問題として現れる。
> **FR では駆動（後輪）と操舵（前輪）が分離する。**
> - 前輪: 横力主体。制動時のみ縦力と複合
> - 後輪: 縦力主体。コーナー脱出時のパワーオンで複合スリップが限界を決める
>
> 後輪の複合スリップがパワーオーバーステアの発生条件そのものなので、
> **FR では「後期」に回さず、AIドライバー（Phase 6）の前に入れる必要がある。**

現在 `tires.effective_radius` は `unknown`。**縦断モデルに必須。** 純正サイズの一次出典を取ってから幾何計算すること。

### 6.4 サスペンションモデル（段階的等価モデル）

**ZN6 の形式: フロント マクファーソンストラット / リア ダブルウィッシュボーン**

公開資料の限界を考慮し、3段階でモデル化する。

- **Level 1**: 単純な等価サスペンション（バネ、ダンパー、ストローク）
- **Level 2**: 推定ジオメトリ（キャンバーゲイン、トー変化、ロールセンター）
- **Level 3**: 詳細な Kinematics モデル（Caster, KPI, Scrub Radius 等）

ダンパーは速度依存の非線形（Compression/Rebound）とし、ARB による左右差の力も計算する。

**形式が前後で異なるため、Level 2 以降のジオメトリ推定は前後で別のモデルになる。** ストラットとダブルウィッシュボーンではキャンバーゲインの傾向が違う。前後で同じ推定式を使わないこと。

現在スプリングレート・ダンパー減衰力・スタビ径・ジオメトリは全て `unknown`。

### 6.5 車体6DoFと慣性

- X, Y, Z, Roll, Pitch, Yaw の独立計算
- 重量だけでなく慣性モーメント（Ixx, Iyy, Izz）を持つ。不明な場合は寸法と重量配分から推定し、**confidence を下げる**
- 加減速・旋回時の荷重移動を計算

#### 荷重移動（FR / CL1版から反転）

| 状況 | 荷重 | FF（CL1） | **FR（ZN6）** |
|---|---|---|---|
| 加速 | 後軸へ移動 | 駆動輪（前）から**抜ける** → トラクション限界が厳しい | 駆動輪（後）に**乗る** → **トラクションが増える** |
| 制動 | 前軸へ移動 | 駆動輪に乗る | 駆動輪から抜ける |

**FR では加速時に駆動輪の荷重が増えるため、発進加速のトラクション限界の扱いが CL1版と逆になる。** 0-100km/h の計算で、荷重移動を無視した定荷重モデルは FR では**過小評価**側に外れる。

#### 重心高（CL1版からの改善）

水平対向エンジンは重心が低い。**直4前提の初期値を置いてはいけない。**

ZN6 はメーカーが「超低重心（重心高460mm）」と公表しているため、Level 2 の探索範囲を大幅に狭められる。ただし出典が販促資料で測定条件が不明なため、`official_marketing` / confidence 0.75 / min 0.44 – max 0.48 として記録している。

## 8. 統合と自動検証システム

### 8.1 物理モデルの自動テスト（Python）

UE5統合（Phase 8）の前に Python 上で単体テストをパスさせる。

- **コンポーネントテスト**: Engine Test, Tire Test, Suspension Test, Brake Test
- **車両挙動テスト**:
  - 直線加速（0-100 km/h）
  - 制動（100-0 km/h）
  - スキッドパッド（定常円旋回）
  - 過渡応答（ステアリングステップ入力）— **FR のため、オーバーステア／スピン判定を含める**

> **0-200 km/h について**
> CL1版は「0-100-200km/h」を検証項目に挙げていた。
> ZN6 の最高速は現時点で `unknown`（`validation_targets.top_speed`）。
> **実測値の出典が取れるまで、0-200km/h を検証項目に置かない。** 比較対象の無いテストは判定できない。

### 8.2 UE5統合と環境構築（Phase 8）

- **分離構造**: 描画メッシュは Visual only。物理計算は独立した Physics Model が担当
- **更新周期分離**: Rendering (60–120Hz), Physics (高頻度サブステップ), Telemetry (50–100Hz)
- **テストコース**: 直線、強ブレーキ、ヘアピン、S字、段差を含む「Physics Test Track」を生成（Phase 7 で Python 側に先に作る）

音響は Phase 14（バックログ）。

### 8.3 AIドライバーとテレメトリー検証

#### AIドライバー（FR 前提）

初期は Racing Line + PID 制御（**事故らず1周が目標**）。安定後に強化学習(RL)を導入し、Lap Time だけでなく安定性・過度なスリップ回避を報酬とする。

> **CL1版（FF）からの変更**
> FF はアンダーステア主体で、限界を超えても「曲がらない」方向に破綻する。PID の目標値追従だけでも1周できる。
> **FR はパワーオーバーステアを起こす。** コーナー脱出時にスロットルを開けすぎると後輪が縦力で飽和し、横力を失ってスピンする。
>
> したがって FR の AIドライバーには以下が要る:
> - **後輪スリップ率の監視とスロットル制限**（トラクションコントロール相当）
> - **ヨーレート偏差によるスピン検出**
> - スピン検出時のカウンターステアまたはスロットル戻し
>
> これを入れずに PID だけで走らせると、コーナー脱出のたびにスピンして「1周する」に到達しない。

#### テレメトリー

Speed, RPM, Throttle, Steering, Gフォース, Slip Angle 等を毎フレーム CSV に記録する。AIが複数周分のログを解析し、異常挙動（**リアの急激なブレイク**等）を検出する。

### 8.4 Reality Validator と Optimizer

シミュレーション結果と実車資料（加速、最高速、横G等）を比較する。

#### 3つの妥当性評価

| 評価 | 内容 |
|---|---|
| **Physics Validity** | 物理法則上妥当か（後述） |
| **Vehicle Validity** | **FR + トルセンLSD + 水平対向低重心**という ZN6 の仕様として妥当か |
| **Empirical Validity** | 実車計測データと一致しているか |

**Physics Validity の判定例（CL1版から差し替え）**

CL1版は「200ps/1400kg で 0-100km/h 3秒はおかしい」を例示していた。**ZN6 は 200PS / 1,230kg であり、この例示にほぼ一致してしまうため例として機能しない。**

ZN6 版では以下を判定基準に置く:

- **タイヤの摩擦限界を超える加速**が出ていないか（μ・荷重・駆動輪荷重から導かれる上限）
- **エンジン出力から導かれる仕事率**を超える加速が出ていないか
- 荷重移動が物理的に成立しない量になっていないか（後軸荷重が車重を超える等）
- **FR で前輪駆動的な挙動**（加速時に前輪がスリップする等）が出ていないか

**「数値が常識的に見えるか」ではなく「保存則と拘束条件を破っていないか」で判定する。**

#### Vehicle Validity（FR の特性）

- コーナー脱出のパワーオンでオーバーステア方向に振れるか（FF なら逆）
- 加速時に後軸荷重が増えてトラクションが向上しているか
- トルセンLSD が作動して内輪空転が抑えられているか
- 低重心（0.46m）に見合ったロール量になっているか

#### Optimizer

誤差が発生した場合、権限レベル（**Level 2〜3 のみ**）に基づき Tire μ, CG Height 等の不確実パラメータを変更し、再シミュレーションを行う。

**Level 0 / Level 1 のパラメータには触れない。** ラップタイムや 0-100km/h を合わせるために公式値を動かすことは、このプロジェクトの目的そのものを破壊する。

> **Optimizer が誤差を吸収してしまう典型例**
> - トルクカーブを2点補間 → 中回転域が速すぎる → Optimizer がタイヤμを下げて辻褄合わせ
> - ファイナルを 3.727 と取り違え → 駆動力が10%不足 → Optimizer がμを上げて辻褄合わせ
>
> **どちらも「入力データの誤り」であって「パラメータの不確実性」ではない。**
> 誤差を見つけたらまず入力データを疑うこと。

- **第3完成目標**: 高品質補正済み3D + PBR + 物理 + 音 + AIドライバー
- **最終完成目標**: 完全な自動キャリブレーションループの確立とレポート出力

### 9.4 Day 1 の作業手順

**データ収集を先に全部やらない。** 14カテゴリのリストを埋める作業になり、何のために集めているかが分からなくなる。代わりに**エンドツーエンドの検証ループを1本通す。**

1. リポジトリと Claude Code の起動 — 完了
2. 公式値の収集 — **完了**（`vehicle.json` に official 38項目）
3. **最小の縦断モデルを Python で書く**（200行程度）— タイヤは定数μ、サスペンションなし、空力は Cd のみ
4. **0-100 km/h を計算し、公開されている実測値と比較する**

#### ここで必ず起きること

ZN6 の 0-100km/h の実測値は情報源によってばらつく（媒体・グレード・仕様地・測定条件による）。**初日から「実測値そのものが不確実」という問題に直面する。**

これは confidence システムが本当に機能するかを確かめる最良のテストケース。**ここで「どの実測値を基準とするか」のルールを決められないなら、Reality Validator（§8.4）は後段で必ず破綻する。**

**採用ルール**: 単一の値を採らず、**複数出典の範囲**として保持し、シミュレーション結果がその範囲に収まるかで判定する。§5.2 が数値に min/max を持たせている思想と一貫する。

**このループが通れば、あとは全部その精緻化。** タイヤモデルを Fiala に、1自由度を6自由度に、と段階的に置き換えていける。

### 10.2 不確実性レポート（Digital Twin Report）

シミュレーターの信頼性を示すため、最終成果物として「完全一致」を主張するのではなく、以下のレポートを出力させる。

```
=================================================
 ZN6 DIGITAL TWIN UNCERTAINTY REPORT
=================================================
 Category           | Score  | Confidence | Status
--------------------|--------|------------|------------------
 Geometry           |   --   |    --      | 未計測
 Engine             |   --   |    --      | 未計測
 Gearbox            |   --   |    --      | 未計測
 Tires              |   --   |    --      | 未計測
 Suspension (K&C)   |   --   |    --      | 未計測
 Brakes             |   --   |    --      | 未計測
 Aerodynamics       |   --   |    --      | 未計測
-------------------------------------------------
=================================================
```

> **CL1版のスコア例（Geometry 91/100 等）は削除した。**
> あれは CL1 を想定した架空の値であり、ZN6 では一度も計測していない。
> **架空の数値をテンプレートに残すと、そのまま実績値として引用される事故が起きる。**
> 憲法「出典のない数値を実測値として扱わない」に反する。

#### スコアの算出方法

| 項目 | 定義 |
|---|---|
| **Score** | そのカテゴリの検証項目のうち、実測値の範囲内に収まった項目の割合 |
| **Confidence** | そのカテゴリのパラメータの `confidence` の加重平均（値の影響度で重み付け） |
| **Status** | `Known / Official`（全パラメータが `official`）／ `Estimated`（`estimated` を含む）／ `Assumed / Optimized`（`assumed` を含む、または Optimizer が変更した）／ `未計測` |

`Audio` は Phase 14（バックログ）で追加する。

- [ ] Physics tick が目標周波数で回っている

## 付録: このプロジェクトの成果物

ZN6 の開発を通してシステム（物理計算パイプライン、自動検証ループ）をテンプレート化することで、以降は入力データを差し替えるだけで別車種への展開が可能なフレームワークが完成する。

**そのために最も重要なのは、`vehicle.json` のスキーマと confidence システムが「実際に機能する」ことを ZN6 で証明することである。** 車種を変えても、変わるのはデータであってパイプラインではない。
