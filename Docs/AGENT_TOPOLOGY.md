# エージェント構成 — 「作るAI」と「疑うAI」の分離

> **このファイルについて**
> チャット側で決まったエージェント構成を、リポジトリ側に確定させたもの。
> `SPEC_CL1_original.md` §2.2 は7ロールをフラットな箇条書きで並べるだけで、
> **誰が誰の下流にいるか**が書かれていなかった。それを明示する。
>
> `HANDOFF.md` §6（2画面分担）との関係もここで決着させる。
>
> 出典: チャット側設計「7. 「AIがAIを評価する」構造にする」「5. AIエージェントによる最終追求」
> 作成日: 2026-08-30

## 0. 結論

1. **Validator は producer の下流に置く。作った本人が採点しない。**
2. **`HANDOFF.md` §6 の2画面分担は、このトポロジの最小実装。** 置き換えではない。
3. **「100点が出るまで回す」評価ループは視覚層でのみ使う。物理層に持ち込むと憲法ルール9違反になる。**

3 が最も重要で、最も間違えやすい。§4 を読むこと。

## 1. トポロジ

```
                 PROJECT MANAGER
                        │
           ┌────────────┼────────────┐
           ↓            ↓            ↓
       Research      Physics         3D
          AI            AI           AI
           │            │            │
           └────────────┼────────────┘
                        ↓
                    Validator          ← 疑うAI
                        ↓
                    Optimizer
                        ↓
                      QA AI
```

### なぜ Validator が下流でなければならないか

**同一コンテキストで自己検算させても意味がない。**

producer は自分の出力を作るときの前提をそのまま持っている。同じ前提で採点すれば、
前提の誤りは検出できない。検出できるのは計算ミスだけで、**このプロジェクトで怖いのは
計算ミスではなく前提の誤り**（グレード列の取り違え、単位の取り違え、2点補間）。

実例: `brakes.rear_type` が G グレードの値だった件は、Validator AI ではなく
**一次資料との突き合わせ**で見つかった。producer がPDFのテキスト抽出を信じたまま
自己検算しても、何度やっても同じ答えが出る（`Docs/SOURCE_A_VERIFICATION.md`）。

### この図が主張していること／していないこと

| | 主張 |
|---|---|
| **している** | Validator は Research / Physics / 3D **すべての下流**にいる |
| **している** | Optimizer は Validator の発見**にのみ**反応する。自発的に触らない |
| **している** | QA が最後のゲート |
| **していない** | 3つの producer が**同時に**走ること |

**横並びは依存関係の話であって、実行が並列であることを要求していない。**
分離の価値はコンテキストが違うことから来ており、同時に動くことからは来ていない。
並列化は §5 の条件を満たしてから。

## 2. 7ロールの定義

`SPEC_CL1_original.md` §2.2 を、入出力と下流関係を明示する形に展開したもの。

| ロール | 責務 | 入力 | 出力 | 下流 |
|---|---|---|---|---|
| **PROJECT MANAGER** | 進行管理、タスクの割り振り、人間への承認要求 | 仕様書、issue | タスク | 全 producer |
| **Research** | 公開資料から実車データを収集・分類 | 公開情報 | `vehicle.json` の項目（`source` / `confidence` 付き） | Validator |
| **Physics** | 物理モデルの実装、テストコード作成 | `vehicle.json` | `Physics/*.py`、テレメトリ CSV | Validator |
| **3D** | 3Dモデルの評価、bpy スクリプト、PBR 設定 | 公開画像、`vehicle.json` の寸法 | メッシュ、テクスチャ | Validator |
| **Validator** | **疑うAI。** producer 全ての出力を監査 | 上記すべて + 一次資料 | 誤差レポート（**修正はしない**） | Optimizer |
| **Optimizer** | Validator が見つけた誤差に対し、不確実パラメータを調整 | 誤差レポート | パラメータ変更案（Level 2〜3 のみ） | QA |
| **QA** | 自動回帰テストの実行、コミット | 変更案 | コミット / 却下 | — |

### 権限の非対称性

**producer は自分の出力を承認できない。Validator は修正できない。Optimizer は Level 0/1 に触れない。**

この非対称性が構造の全て。1つでも崩すと、単一のAIが「作って・採点して・直す」ループになる。

| ロール | `vehicle.json` への書き込み | `Physics/` への書き込み | コミット |
|---|---|---|---|
| Research | **○（唯一の書き手）** | × | × |
| Physics | × | ○ | × |
| 3D | × | × | × |
| Validator | **×（読むだけ）** | × | × |
| Optimizer | ×（**変更案を別ファイルに出す**） | × | × |
| QA | × | × | ○ |

**`vehicle.json` の書き手を Research 1つに限るのが要。** §5 の競合問題がこれで消える。
Optimizer が Level 2〜3 を触りたい場合も、直接書かずに変更案を出し、QA がテストを通してから反映する。

## 3. Validator は何を根拠に判断するか

**ここを縛らないと Validator も捏造する。** Validator も LLM であり、
「もっともらしい判定」を生成できてしまう。

### 3つの妥当性と、それぞれのオラクル

`SPEC_ZN6.md` §8.4 の3分類に、**何が正解を決めるか**を紐づける。

| 妥当性 | 問い | オラクル（正解を決めるもの） |
|---|---|---|
| **Physics Validity** | 物理法則を破っていないか | **保存則と拘束条件。** タイヤ摩擦限界、エンジン仕事率、軸荷重の合計、スリップ率の定義域 |
| **Vehicle Validity** | ZN6 の仕様として妥当か | **`vehicle.json` の `official` 項目。** FR、トルセンLSD、重心高 0.46m、ファイナル 4.100 |
| **Empirical Validity** | 実測データと一致するか | **`validation_targets` の範囲。** 単一値ではなく複数出典の min/max |

### Validator の拘束

1. **判定には必ず根拠を紐づける。** 「妥当でない」だけの出力は却下。
   どの保存則か、`vehicle.json` のどのフィールドか、どの出典の範囲かを示す
2. **「常識的に見えるか」で判定しない。** 元仕様書の例示「200ps/1400kg で 0-100km/h 3秒は
   おかしい」は、ZN6（200PS/1230kg）にほぼ一致してしまい機能しない。
   常識ではなく**保存則と拘束条件**で判定する（`SPEC_ZN6.md` §8.4）
3. **`unknown` を埋めない。** Validator が「たぶん 0.316m」と補完したら、それは
   Research の仕事を無出典でやったことになる。憲法ルール14違反
4. **修正しない。** 誤差を報告するところまで。直すのは Optimizer、通すのは QA
5. **誤差を見つけたら、まず入力データを疑う。** パラメータの不確実性より、
   入力の誤りの方が頻度が高い（グレード取り違え、単位、2点補間）

### Validator が最初に疑うべきリスト

過去に実際に起きた／起きうる入力データの誤り。

- **グレード列の取り違え** — 諸元表は6列ある。1列ずれると別グレードの値になる（実際に起きた）
- **ファイナルの variant** — GT は 4.100、G 6MT のみ 3.727。約10%の駆動力誤差
- **全高とルーフ高** — 1,320 はアンテナ込み。ルーフ高は 1,285
- **トルクカーブの2点補間** — FA20 の 4,000rpm 付近の谷が消える
- **単位** — km/h と m/s、PS と kW、mm と m
- **前期／後期** — 後期は 152kW / 212N·m

## 4. 評価オラクルは層によって違う（最重要）

### 前例

チャット側の設計「5. AIエージェントによる最終追求」に、別プロジェクト（ゲーム制作）での
実績が記録されている。

> Claude のサブエージェントシステムを活用。「物理挙動担当」「グラフィック担当」といった
> 複数のAIエージェントを並列で走らせ、各担当の成果物を「超辛口評価担当」のAIが判定。
> **100点満点が出るまで何度も修正を繰り返す**体制でブラッシュアップした。
>
> 結果: マテリアルの質感向上（つや出し）、ライトの点灯機能、ナンバープレートの追加、
> 背景（山・雲・海）の作り込みが実現した。

**この体制は有効だった。ただし成果は全て視覚要素である。** これは偶然ではない。

### なぜ視覚層で機能し、物理層で事故になるか

**「100点が出るまで回す」ループが健全なのは、評価者が正解そのものであるときだけ。**

つや、ライト、背景の作り込みに客観的な正解は無い。**「良く見えるか」が正解**であり、
評価者の主観がオラクルとして正しい。だから収束するまで回してよい。

物理は違う。**0-100km/h の正解は実測値であって、評価者のスコアではない。**
スコアを上げるループを回すと、評価者を満足させる方向に最適化が進む。実車から離れても
スコアは上がりうる。これは憲法ルール9「ラップタイムだけを合わせる最適化の禁止」
そのものである。

| 層 | 対象 | オラクル | 収束条件 | 「100点まで回す」 |
|---|---|---|---|---|
| **視覚** | メッシュ、マテリアル、背景、UI | **評価者の主観そのもの** | 評価者が満足 | **○ 正しい** |
| **音響** | エンジン音、路面音 | 主観 + 実車動画との突き合わせ | 主観の満足 + 明らかな乖離が無い | △ 条件付き |
| **物理** | 加速、制動、旋回、荷重移動 | **実測値の範囲と保存則** | 範囲に収まる。**スコアではない** | **✗ 禁止** |
| **データ** | `vehicle.json` | **一次資料。それだけ** | 出典と一致 | **✗ 論外** |

### 実装への帰結

- **視覚層（Phase 9〜15）では「超辛口評価担当」を置き、収束まで回してよい。**
  `Docs/SPEC_PHASE2_BACKLOG.md` の Reference Renderer ループは既にこの形（誤差が閾値を
  下回るまで繰り返す）。評価者を追加するのは自然な拡張
- **物理層（Phase 4〜8, 16〜17）では点数を付けない。** Validator は
  「範囲に収まっているか / 保存則を破っていないか」の**二値**で答える。
  スコアを出すと、それを上げるループが生まれる
- **`SPEC_ZN6.md` §10.2 の Digital Twin Report のスコアは、最終報告であって最適化目標ではない。**
  あのスコアを上げるために Optimizer を回してはいけない。CL1版の架空スコアを削除したのも
  同じ理由（実績値として引用される事故を防ぐため）

**この区別は、憲法ルール6「物理計算と表示用3Dモデルを完全に分離する」の評価版である。**
分離すべきなのはモデルだけでなく、**それぞれを何で採点するか**も分離される。

## 5. 並列にする前に満たすこと

図の横並びを**実行の並列**にする場合、以下が未解決だと事故になる。

### 5.1 `vehicle.json` の同時書き込み

**層1のフックはコミット時にしか効かない。** 並行編集中は無防備で、後から書いた方が勝つ。

**対策: 書き手を Research 1つに限る**（§2 の権限表）。Physics / 3D / Validator は読むだけ。
Optimizer は変更案を別ファイルに出し、QA が反映する。

これで「同時書き込み」という状況自体が発生しない。ロック機構は要らない。

### 5.2 コンテキスト分離が壊れる条件

**同じセッションからサブエージェントを撒くと、分離が名目だけになる。**

サブエージェントは白紙から始まるが、**受け取るプロンプトは親が書く。**
親の思い込みがプロンプトに乗れば、下流の Validator はその前提を継承する。
「別コンテキスト」ではなく「親の前提のコピー」になる。

分離の強さの順:

| 手段 | 分離の強さ | 備考 |
|---|---|---|
| **コミット前フック** | **最強** | コンテキストを持たない。説得できない |
| 別セッション / 別画面（チャット） | 強 | 前提を共有しない。`HANDOFF.md` §6 の方式 |
| GitHub Actions での検証 | 強 | 機械的。人の介在なし |
| 同一セッションのサブエージェント | **弱** | プロンプト経由で親の前提が流れる |

**Validator を同一セッションのサブエージェントで実装する場合は、
プロンプトに結論を書かず、一次資料へのパスと判定基準だけを渡すこと。**
「この値が正しいか確認して」ではなく「諸元表を描画して GT 6MT 列を読み、
`vehicle.json` と突き合わせて差異を列挙して」と書く。

### 5.3 コスト

producer 3つ + Validator + Optimizer + QA を毎回フル稼働させると、
1サイクルのコストが跳ね上がる。**Phase 4〜8 の段階では過剰。**

段階的に増やす（§6）。

## 6. 現在の実装状況

### すでに動いている「疑うAI」

**層1のコミット前フックが、機械化された Validator として稼働している。**

- Level 0 パラメータの変更を検出して止める
- `vehicle.json` のスキーマ違反を止める
- pytest 失敗を止める

**コンテキストを持たないので説得できない。** これが最も強い分離（§5.2）。
LLM の Validator が要るのは、機械化できない判断だけ。

### 2画面分担はこのトポロジの最小実装

`HANDOFF.md` §6 の分担は、7ロールを2つの面に畳んだもの。**置き換えではない。**

| トポロジ上のロール | 現在の実装 |
|---|---|
| PROJECT MANAGER | 人間 |
| Research | チャット（claude.ai） |
| Physics | Claude Code |
| 3D | **未稼働**（Phase 10〜） |
| **Validator** | **チャット（claude.ai） + 層1フック** |
| Optimizer | **未稼働**（Phase 17〜） |
| QA | Claude Code + 層1フック |

**Validator が Physics と別の面にいる**ため、下流関係は保たれている。

### 段階的な拡張計画

| Phase | 追加するロール | 理由 |
|---|---|---|
| 4〜8 | 現状維持（2画面 + フック） | producer が Physics 1つしかない。分割する対象がない |
| 16 | **Validator を独立させる** | 実測比較が本格化する。判定根拠の拘束（§3）を実装 |
| 17 | **Optimizer を独立させる** | パラメータ探索。Level 2〜3 の権限をフックで縛る |
| 10〜13 | **3D + 超辛口評価担当** | 視覚層。§4 のとおり収束まで回してよい |
| 14 | Audio + 評価担当 | 同上（条件付き） |

**Phase 4 の時点でロールを7つに割らないこと。** producer が1つしかない段階で
分割しても、オーバーヘッドだけが増える。

## 7. `AI/` ディレクトリ

`SPEC_ZN6.md` §4 の構造に `AI/`（AIエージェント用プロンプト）がある。**現在は空。**
「先に空ディレクトリを作らない」方針のため、まだ作っていない。

ロールプロンプトを置くのは **Phase 16（Validator の独立）から。** 置くときの構成:

```
AI/
├── roles/
│   ├── validator.md      # 判定基準と拘束（§3）。結論を書かない
│   ├── optimizer.md      # 権限 Level 2〜3 の明示。変更案の出力形式
│   ├── research.md       # 出典の優先順位、source/confidence の付け方
│   └── critic-visual.md  # 超辛口評価担当（視覚層のみ / §4）
└── README.md             # このファイルへの参照
```

**ロールプロンプトに結論や期待値を書かないこと**（§5.2）。渡すのは
一次資料へのパス、判定基準、出力形式だけ。
