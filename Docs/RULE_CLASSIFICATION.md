# 憲法18ルールの三層分類 — 分類理由の記録

> **このファイルについて**
> `SPEC_CL1_original.md` §5.1 の18ルールを、`HANDOFF.md` §3 の三層構造にどう振り分けたかの記録。
> **なぜその層に置いたか**を残すのが目的。分類を変えるときはここも更新すること。
>
> 作成日: 2026-08-30

---

## なぜ分割したか

元仕様書は18ルールを `AGENTS.md` 1枚に並べる想定だった。これには2つの問題がある。

1. **`CLAUDE.md` はコンテキストであって強制設定ではない。**
   「Level 0 パラメータを変更しない」と書いても、それは読ませているだけで、
   実際に変更を止める仕組みではない。**確実にブロックしたい項目はフックで実装しないと守られない。**

2. **1ファイルが長いほど遵守率が下がる。**
   18ルールを常時読ませると、そのうち本当に判断を要するのは6つで、
   残りは機械的に検証できるか、特定のファイルを触るときしか関係ない。
   常時読み込むコンテキストは、判断を要するものだけに絞る方が効く。

## 三層の定義

| 層 | 場所 | 性質 | 読み込みタイミング |
|---|---|---|---|
| **層1** | `.claude/hooks/` | **機械的に検証できる。** AIの判断に関係なく実行される | コミット時 |
| **層2** | `CLAUDE.md`（150行以内） | **判断を要する。** 機械化できない | 全セッション |
| **層3** | `.claude/rules/*.md` | **パス限定。** `paths` フロントマターでスコープ | 該当ファイルを触るときだけ |

### 振り分けの判定基準

上から順に当てはめた。

1. **スクリプトで真偽を判定できるか** → できるなら**層1**
2. **特定のディレクトリのファイルを触るときしか関係ないか** → そうなら**層3**
3. **どのファイルでも常に効き、かつ判断を要するか** → **層2**

**層2 に置くものを最小にする**のが目的。常時読み込むコストを払う価値があるものだけを残す。

## 層をまたぐルールについて

**8つのルール（2, 5, 6, 8, 11, 13, 16, 17）は複数の層に分かれている。** これは分類の失敗ではなく、
**「機械で検証できる部分」と「判断が要る部分」が同じルールの中に同居している**ためである。

代表例:

### ルール2「出典のない数値を実測値として扱わない」

- **層1**: `source` フィールドが存在するか、値が6分類のいずれかか → 機械判定できる
- **層2**: その `source` が妥当か。「一般的に知られている」を `measured` と書いていないか → 判断

層1だけだと、`source: "measured"` と書きさえすれば通ってしまう。**層1は嘘を弾けない。**

### ルール16「回帰テスト失敗の状態で完成扱いにしない」

- **層1**: pytest が失敗したらコミットを止める → 完全に機械化できる
- **層3**: そもそもテストを書いているか、skip や `xfail` で誤魔化していないか → physics.md

**層1は「テストが失敗していないこと」しか見ない。「テストが存在すること」は見ていない。**

## 層1 が実装するもの（3項目）

`HANDOFF.md` §3 層1 の指定どおり。

| # | 検査 | 対応ルール |
|---|---|---|
| 1 | **Level 0 パラメータの変更検出** — 排気量・ホイールベース・公式ギア比・公式車重が `vehicle.json` で変更されたらコミットを止める | 11 |
| 2 | **`vehicle.json` のスキーマ検証** — `source` / `confidence` / `unit` の必須、SI単位、`"unknown"` の許容 | 3, 4, 5, 13, 14 |
| 3 | **pytest 失敗時のコミット停止** | 16 |

### Level 0 に variant 保護を追加した

元仕様書 §5.3 は Level 0 を「公式ギア比」としか書いていない。

**ZN6 のファイナルは単一値ではない**（G 6MT のみ 3.727、他 4.100）ため、
**値だけを監視しても variant の取り違えは検出できない。**
フックは `final_drive.value` と `final_drive.variants` の両方を監視する。

根拠: `Docs/ZN6_BASELINE.md` 罠①

`HANDOFF.md` §3 の指定どおり。

### 未解決: `Tests/` が層3のスコープに入っていない

`HANDOFF.md` は `physics.md` のスコープを `Physics/**/*.py` と指定している。
しかし**物理コードのテストは `Tests/` に置く設計**（`SPEC_ZN6.md` §4）であり、
ルール8（テストを追加/更新する）・ルール10（複数指標で比較する）・
ルール15（物理的にあり得ない値を検査する）は `Tests/` を書くときにも効くべきものである。

現状は `HANDOFF.md` の指定に忠実に `Physics/**/*.py` のみとした。

**Phase 4（物理モデル実装）でテストを書き始めたときに、
`paths: ["Physics/**/*.py", "Tests/**/*.py"]` へ広げるか判断すること。**

## ファイル名について

Claude Code が読むのは `CLAUDE.md` であり `AGENTS.md` ではない。
他のエージェントを併用する予定がないため、**`CLAUDE.md` 一本**とした。

併用することになった場合は、`AGENTS.md` を本体にして
`CLAUDE.md` の先頭に `@AGENTS.md` と書いてインポートする。

## 仕様書全文を CLAUDE.md に入れないこと

`Docs/SPEC_ZN6.md` は653行ある。これを常時読み込むと、
**判断を要する6ルールが653行の中に埋もれる。**

`SPEC_ZN6.md` は自動ロードせず、必要なときだけ読む。
`CLAUDE.md` にはドキュメントの一覧と、どれをいつ読むかだけを書いてある。
